# P1.7 — Pricing de três tiers + cap de tamanho por orçamento

**Prioridade:** P1
**Tipo:** feat
**Branch:** `feat/p1-7-pricing-3-tiers`
**Esforço estimado:** 1-2 dias
**Depende de:** P0.3 (telemetria de tokens — para conferir gasto por orçamento), P0.4 (hard limits expostos), P1.5.1 (config de empresa funcional)

## Objetivo

Implementar três planos no Stripe — Avulso (já existe), Profissional (já existe), Empresarial (novo) — com **limite de tamanho de orçamento por plano**. A planilha de unit economics (Entregável B) mostrou que o plano mensal sem cap tem margem 0,4% em obras grandes. Esse ticket resolve o buraco de margem antes da primeira venda comercial.

## Contexto

Decisões já travadas (do Entregável E):

| Plano | Preço | Quota | Cap por orçamento |
|---|---|---|---|
| Avulso | R$ 89,90/orç. | 1 | sem cap |
| Profissional | R$ 450/mês | 10 orçamentos | 100 itens / 20k tokens de memorial |
| Empresarial | R$ 990/mês | 25 orçamentos | 300 itens / 50k tokens de memorial |
| White-label | R$ 2.500/mês + R$ 30/orç. | ilimitado | sem cap |

A landing pública (`engine.rres.com.br`) já mostra os 4 planos. O app real (`rrengine.manus.space`) ainda só tem 2 (Profissional R$ 450 + Avulso R$ 89,90). White-label fica como conversa privada — não entra no Stripe ainda.

## Decisão técnica — onde guardar o plano

### Opção A — colunas na tabela `users`

```ts
plan_type: mysqlEnum('plan_type', ['avulso', 'profissional', 'empresarial', 'white_label']).default('avulso'),
plan_quota_remaining: int('plan_quota_remaining').default(0),
plan_quota_resets_at: timestamp('plan_quota_resets_at'),
```

Simples. Funciona para 1 usuário = 1 plano. Sem histórico de mudanças.

### Opção B — tabela `subscriptions` separada

```ts
export const subscriptions = mysqlTable('subscriptions', {
  id: bigint('id', { mode: 'number' }).primaryKey().autoincrement(),
  userId: int('user_id').notNull().references(() => users.id),
  stripeSubscriptionId: varchar('stripe_subscription_id', { length: 100 }).unique(),
  planType: mysqlEnum('plan_type', ['profissional', 'empresarial', 'white_label']).notNull(),
  status: mysqlEnum('status', ['active', 'past_due', 'canceled', 'trialing']).notNull(),
  currentPeriodStart: timestamp('current_period_start'),
  currentPeriodEnd: timestamp('current_period_end'),
  quotaUsed: int('quota_used').default(0),
  createdAt: timestamp('created_at').defaultNow(),
  updatedAt: timestamp('updated_at').defaultNow().onUpdateNow(),
}, (t) => ({
  userIdx: index('idx_user_status').on(t.userId, t.status),
}));
```

Suporta histórico, múltiplos planos por usuário (raro, mas não impossível), eventos de migração de plano. Mais complexo.

**Recomendação:** **Opção B**. Hoje o Stripe mantém o histórico real, e quando alguém sobe de Profissional para Empresarial, queremos preservar o registro do plano antigo. Modelo de assinaturas em SaaS B2B sempre vira opção B em algum momento — fazer agora evita migração dolorida depois.

- [ ] Em `server/routers.ts`, criar middleware tRPC `requireQuotaAvailable`:
  ```ts
  const requireQuotaAvailable = middleware(async ({ ctx, next }) => {
    const limits = await getCurrentPlanLimits(ctx.userId);
    if (limits.quotaRemaining <= 0) {
      throw new TRPCError({
        code: 'TOO_MANY_REQUESTS',
        message: 'Quota mensal atingida. Atualize seu plano ou aguarde o próximo ciclo.',
      });
    }
    return next({ ctx: { ...ctx, planLimits: limits } });
  });
  ```

## Observações

- O ticket assume que Stripe Connect / pagamento Pix já está funcional (já está em produção). Se mexer no fluxo de pagamento, escalate para issue separada.
- White-label NÃO entra neste ticket — será conversa privada com escritórios. Processamento manual via boleto/PIX direto, sem Stripe nesta fase.
- Quando primeiro cliente Empresarial entrar, validar com a planilha de unit economics que a margem real bate com o estimado. Se desvio > 30%, abrir issue para revisar pricing.
- Estratégia de migração: usuários com Profissional ativo continuam Profissional. UI ofereceu upgrade voluntário para Empresarial. Não há migração forçada.
- Tem efeito legal/contratual: a alteração de pricing (introduzir Empresarial) precisa ser comunicada nos Termos de Uso já publicados em `engine.rres.com.br/termos`. Não é obrigatório atualizar agora, mas a próxima revisão dos termos deve refletir os 3 tiers.
